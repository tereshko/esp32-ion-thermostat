# FIRMWARE-ANALYSIS-L — Stage L: полный ценз писателей в RAM-блок модуля zone-demand (0xFFF8C800–0xFFF8CE00)

Образ: `ion-firmware/carrier/BINF0479_Carrier.hex` (бинарь), Renesas SH-2A BE, база flash 0x18040000, offset = адрес − 0x18040000. Работа велась на копиях в `firmware-re/stageL/` (проект Ghidra — копия stageE; stageB–E не тронуты). Промежуточные файлы: `firmware-re/stageL/out/` (`census.txt`, `census_classified.json`, `rawscan_cells.txt`, `decomp/*.c`, `pools/*.txt`, `list_L.txt`, `users_L.txt`, `appendix_writers.md`).

## 0. Вердикт

**Все ключевые входы модуля zone-demand (stage E) имеют найденных писателей.** Ни один из них не берётся «ниоткуда»: блок 0xFFF8C800–0xFFF8CE00 — это рабочее зеркало Clarinox-модели, которое наполняют два контура:

1. **Контур внесения (ingestion)** — диспетчер **FUN_181f5d08** копирует данные из хранилища полей (field store), его RAM-зеркал (0xFFF82xxx/0xFFF83xxx) и словарного пространства (0x3C0Dxxxx) в блок и **вычисляет** таблицы порогов по классу оборудования.
2. **Контур решения (refresh)** — **FUN_181efdfc** (stage E) вызывает производителей demand-цепочки: FUN_1816deec → FUN_1814c9ba → FUN_180c62fc → FUN_1816e2dc (+ функции stage E §2–§7).

**Таблица порогов 0xFFF8CCC4 из flash НЕ копируется** — шаблона в образе нет. Она (и две родственные таблицы 0xFFF8CCDC и 0xFFF8CD04) **вычисляется** функцией FUN_181f21d4 по формулам, зависящим от слова класса оборудования; константы формул извлечены дословно (§4). Для эмулятора это означает: таблицу нельзя «снять» из прошивки готовой — её надо либо читать с живого термостата, либо воспроизводить формулы FUN_181f21d4 по классу оборудования Антона.

Не изолированы писатели только у 7 второстепенных ячеек CAxx (§7) — ни одна не входит в список ключевых входов stage E.

## 1. Метод и покрытие

Двойной метод stage C, как заказывалось:

- **Канал 1 (Ghidra):** скрипт `WriterCensus.java` — все literal-pool слова образа, попадающие в диапазон 0xFFF8C800–0xFFF8CE00, + все прямые references (WRITE/READ/PARAM/DATA) на них.
- **Канал 2 (сырой скан):** независимый Python-скан flat_trim.bin по тем же значениям.

**[FACT] Оба канала дали тождественный результат: 195 различных значений-баз, 1171 вхождение ячеек.** Типы прямых refs по образу: WRITE 686, READ 1449, PARAM 152, DATA 128; всего use-сайтов 3172.

Классификатор (трекинг регистра указателя по окнам ±14 инструкций + resolved refs) отнёс писателей к **210 из 233** ячеек, имеющих хоть какие-то refs. Остальные 23 разрешены вручную по декомпиляциям (§3, §7): 15 из них пишутся через **PARAM-канал** — адрес ячейки передаётся аргументом в helper копирования/чтения поля (FUN_1823d404 / FUN_1815927c), поэтому прямой WRITE-инструкции в вызывающей функции нет; механический писатель — helper, производитель — вызывающая функция.

Ключевые функции декомпилированы (12+2 шт., `out/decomp/`) и их pool-ячейки разрешены по сырому образу (`out/pools/`); головные утверждения сверены по листингу (`out/list_L.txt`, 4337 строк) — второй независимый метод для §3–§4.

## 3. Карта происхождения входов

Обозначения: **[F]** — факт (декомпиляция + разрешение pool по образу, головные места сверены с листингом); **[I]** — inference.

### 3.1 Demand float 0xFFF8CD44 — два писателя

**[F] Писатель 1 — FUN_180c62fc** (агрегатор, вызывается из refresh FUN_181efdfc). Финальный store: `fmov.s fr2,@r1 → 0xFFF8CD44` @ **0x180c6784** (листинг, строка 3541 файла list_L.txt). Значение: `CD44 = C90C`, где C90C — аккумулятор: в начале цикла обнуляется (`*C90C = const`, pool DAT_180c6570→C90C), затем по каждой из 8 зон прибавляется обработанный вклад. Вклады зон строятся helper-ами FUN_180c5dd0 / FUN_180c5e00 / FUN_180c5e16 / FUN_180c5e3c / FUN_180c5ebc / FUN_180c5fc6 из массивов CABC, CADC, CB60, C880, C8CC, C8EC, CA04, CA24, CD1C и клампятся массивами C880/C8EC; ворота цикла — mode byte CD7D (`== 3` → ветка FUN_180c5f5c) и флаг CBDC (через FUN_180c5d90() > 1 && *CBDC != 0). В конце вызывает FUN_180c61a4. Также пишет CE64 (сумма модулей вкладов) и CE60 (затухающая поправка: `CE60 = max(CE60 − FUN_180c613a(), floor)`) — обе ячейки **вне** диапазона ценза (0xFFF8CE60/64 > CE00), отмечены как граничные.

**[F] Писатель 2 — FUN_180c4322(float, table_base)** (store `*DAT_180c4404 = param_1`, pool→CD44). Это ветка `case 2` пятиканального диспетчера **FUN_180c406e** (селектор — FUN_180c4224()) из соседней binding-группы 0x180C4xxx (не из refresh-цикла). Функция складывает аргумент в CD44 и параллельно ведёт служебные байты CA75/CA76/CA94 и зеркала 0xFFF874xx; условие внутри: `table[idx] × 0.5 <= CD44`, где table — база, переданная вызывающим, idx — байт из 0xFFF874D0, константа 0.5 — pool DAT_180c4414 = 0x3F000000. **[I]** Это альтернативный зарегистрированный вычислитель того же свойства в другой группе; какая группа «выигрывает» в конкретном цикле — вопрос планировщика Clarinox, статически не решается. Для эмулятора релевантен писатель 1: он внутри zone-demand refresh.

### 3.2 Таблица порогов 0xFFF8CCC4 и родственные таблицы — FUN_181f21d4

**[F] Единственный писатель CCC4, CCDC и CD04 — FUN_181f21d4** (6390 байт; exact + indexed в цензе; pool-ячейки DAT_181f24a0→CCC4, DAT_181f24a8→CCDC, DAT_181f24ac→CD04). В stage E эта функция числилась «потребителем» — **это исправлено: она главный производитель таблиц и индекса** (§6).

Входы FUN_181f21d4 (все — листинг головы функции, `list_L.txt` строки 2–60):

В конце: при `(CC52 & 0x7C00) == 0x4000` вызывается **FUN_181f3f44** — писатель байтов CBB1/CBB3 (§3.3).

### 3.3 Индекс 0xFFF8CC5A — два писателя, оба разрешены

**[F] FUN_181f21d4:** `CC5A = (CC52 & 0xF) + 1` в основном пути; `CC5A = 1` в fallback-ветке (store @ **0x181f2280**, листинг: `mov #0x1,r1; mov.b r1,@r7 → fff8cc5a`). То есть индекс — **функция младшего нибла слова класса оборудования**, а не счётчик и не таймер.

**[F] FUN_1814c9ba** (636 байт; вызывается из refresh и из FUN_180c4fcc): при поднятом флаге CD79: если `(CC52 & 0x7C00) == 0x4000`: при CD7D == 2 → `CC5A = CBB1 + 1`, иначе `CC5A = CBB3 + 1`; если класс не 0x4000 → `CC5A = 2`. Байты CBB1/CBB3 пишет FUN_181f3f44 (хвост FUN_181f21d4). Та же функция выводит наружу байт CD78: `FUN_180d04dc(0x20, 0xC3, CD78)` — репорт вычисленного байта в словарь/на шину по адресу 0x20, поле 0xC3.

### 3.4 Слово класса 0xFFF8CC52 — «mode nibble» stage E

**[F]** CC52 — не нибл режима, а **16-битное слово класса/типа оборудования**: читается как word (`mov.w @r1,r7` @181f225a), сравнивается с полными кодами 0x8000, 0x8241, 0x92C1, 0x8141, 0x91C1, 0x8242, 0xA2C2, 0x8142, 0xA1C2, 0x92C2, 0x91C2, 0x85C2, 0x8AA2, 0x89A2, 0x8EA2, 0x8DA2, 0xC295, 0xC195, 0xC6A2, 0xC5A2, 0xCAA2, 0xC9A2. Писатель — чтение поля 1 field store внутри FUN_181f21d4 (PARAM-канал, §3.2). Наблюдение stage E «CC52 & 0xF < 2» — чтение младшего нибла того же слова другим потребителем. **[I]** Коды вида 0x82xx/0x92xx/0xA2xx — закодированный тип+размер оборудования из комишенинга; какой код у установки Антона, статически не определяется — слово приезжает в field store в рантайме.

### 3.5 Mode byte 0xFFF8CD7D — три писателя, источник — зеркало C5A0 и getter-ы

**[F] FUN_181f4308** (1190 байт): в голове копирует 11-байтную запись зеркала 0xFFF82E0D → запись **0xFFF8C5A0** (вызов FUN_1823d404(C5A0, 0xFFF82E0D, 0xB)), затем `CD7D = C5A0[0]`, и зеркалит CD7D обратно в 0xFFF83E2C. Та же функция — производитель **CD8C**: линейная интерполяция по таблицам **CC34** (индексы CA59/CA5A), **CCC4** (индексы CA75/CA76), **CCDC** (те же индексы) с getter-ами FUN_181f77f4/FUN_181f7822; выбор по CD7D: `CD8C = (CD7D==2) ? interp(CCC4) : (CD7D==1) ? interp(CC34)+interp(CCDC) : interp(CCDC)`; далее `C90C = CD8C` (второй писатель аккумулятора из §3.1!), `C9EC = <CCDC-interp>`, и равный сплит по активным зонам: `C8CC[i] = CD8C / n_active` (активность — FUN_181f035c(i)), неактивным C9AC[i]=C8CC[i]=0. Плюс байты: CB4D=1, CD3F=1, CD43=1, CD48=0, CD4A∈{0,4}, CD4B=4, CD78=0, CD7B=CA80, CD7C=CA94, CD86=(CA80||CA94), CD7E..CD85=0x0F, CDFC=0.0, C9F0=0.

**[F] FUN_181f5d8a** (272 байта): `CD7D = FUN_181f6ffe()`, при нуле — `FUN_1815da86()` (store через pool DAT_181f5fa8→CD7D). Заодно считает C874/C878 = max из двух индексированных getter-ов FUN_180504f2(CC5A−1), FUN_18050a68(CC5A−1) и табличного CC1C[CBFA−1].

**[F] FUN_181efdfc** (refresh stage E) — третий писатель (копии/обновления в своём цикле, зафиксирован ещё в stage E).

**[I]** Все три пути сходятся в одном: значение режима рождается **вне** блока — в зеркальной записи C5A0 (копия из 0xFFF82E0D) и в Clarinox getter-ах словаря; блок лишь хранит результат. Производитель записи 0xFFF82E0D — слой field store (stage C), не этот модуль.

### 3.6 Входы §4 stage E: X (CB58), Y (CABB), ворота CB5C

**[F] CB58 (X, float)** — единственный писатель **FUN_181f59e0**: прямой store `fmov.s fr2,@r1 → 0xFFF8CB58` @ **0x181f5b62** (листинг). Источник — float-ячейка зеркала (pool DAT_181f5c84; вне блока). Та же функция наполняет: **CB60[8]** — bulk-копия 0x20 байт helper-ом FUN_1823d404 (dest CB60 @181f5b70–181f5b76, листинг), **CB5C** — копия 1 байта тем же helper-ом (dest CB5C @181f5b66, листинг), **CBA9[i]** — обнуление/установка флагов, **CBDC** ← зеркало, **CBB8** ← поле 0x6C (4 байта), **CBBC[8]** ← поле 0x70 (0x20 байт = 8 float; значения валидируются в диапазон (0, 1.0]), CB50/CB54/CB55/CB56 — копии из зеркал, CBA0 (8 байт), CBA8 — байт №17 из 0x1B-байтной записи поля, CBB5=0.

**[F] CABB (Y)** — писатель разрешён: **FUN_181f54e8**, первый же вызов — копия 1 байта FUN_1823d404(CABB, **0xFFF83C92**, 1); адрес CABB подан как PARAM @ **0x181f54ee** (листинг). Источник — байт зеркала 0xFFF83C92. Гипотеза «CABB внутри массива от CAAB» **отклонена**: FUN_180c61a4 пишет ровно CAAB[0..7] и CAB3[0..7] (pool DAT_180c62e8→CAAB, DAT_180c62ec→CAB3), CABB = CAB3+8 — отдельная ячейка сразу за массивом.

**[F] FUN_180c61a4** (вызывается из FUN_180c62fc): при CAA9 != 0 и CBDC != 0, для активных зон (FUN_181f035c) при `C8CC[i] <= C880[i]` выставляет комплементарные флаги CAAB[i]/CAB3[i] по байту CB2E[i]. Писатель CAA9 — FUN_180c15d2 (ценз); писатель CB2E — FUN_18052410 (indexed, ценз).

**[F] FUN_181f54e8** — главный «ингeстор» зональных массивов: **CABC[8] ← копия из зеркала 0xFFF83C58** (0x20 байт), **CADC[8] ← копия из зеркала 0xFFF83C38** (0x20 байт), CB49 ← поле 0x3E, CB46 ← поле 0x27, CB47 ← поле 0x36, CBDD ← поле 0xBF, CD10 ← поле 0x53, CD11 ← поле 0x54, CB4A ← копия из 0xFFF83D24, CB0E/CAFE (short-массивы) ← (short)float-массива словаря 0x3C0D8F74, CB36[i] ← (поле 0x4A, байт i) == 0x1A, CB3E ← копия из 0xFFF82EE5, CAFC ← копия из 0xFFF82EED, CBE0..CBF0 ← зеркала 0xFFF833xx с клампом (при < парного или < 1.0 → 3.0/0.0), CB4B/CB4C ← логика от CB49 и getter-ов FUN_181f7958/FUN_181f79e8/FUN_181f6ed4/FUN_181f6cb8, CD12/CD13 ← логика от CD7D и полей 0x37/0x38, CD14 ← (float)поле 0x47, CD18 ← (float)поле 0x48, CD70 ← (поле 0xCD == 0), CB4D=0.

### 3.7 Зональная цепочка §2–§3 stage E: C9CC и C9AC (поправка к ярлыкам A/B)

**[F] FUN_1816deec** (894 байта; из refresh) пишет **C9CC[8]** — не CABC, как можно было прочитать из классификатора (та атрибуция — артефакт трекинга: CABC/CADC в этой функции только **читаются** как источники копий; то же про «CB60 — писатель FUN_1816e2dc»: там CB60 только читается). По mode byte CD7D:
- CD7D==1: база = CADC[i], отслеживаемый max → C9A8 (seed 50.0), смещение **+0.75**;
- CD7D==2: база = CABC[i], отслеживаемый min → C9A8 (seed 90.0), смещение **−0.75**;
- иначе: база = CADC[i], seed C9A8 = 70.0, смещение +0.75.
Неактивная зона (getter FUN_181f0428(i) == 0) → 0.0. Активная: если CBA9[i]==1 → `C9CC[i] = база[i] + смещение`, иначе `C9CC[i] = C9A8 + смещение`. Под-ветка (бит i в *(ushort*)CB4A, CD7D==2, CD4B∈{1,2}): флаг C8BC[i] = (CB60[i] > CD50[i] + t), t = 0.5 или 0.0 по (C8BC[i], CD4A); и `C9CC[i] = min(C9CC[i], CD50[i] + t)` — то есть §6-trim CD50 капает C9CC.

**[F] FUN_1816e2dc** (326 байт; из refresh) пишет **C9AC[8]** и сумму **C9EC**: по зонам, активность — FUN_181f0428(i): CD7D==1 → `diff = C9CC[i] − CB60[i]`; CD7D==2 → `diff = CB60[i] − C9CC[i]`; иначе 0; `C9AC[i] = max(CA04[i] × diff, 0.0)`; `C9EC = Σ C9AC[i]`.

**[I]** Семантика цепочки: CABC/CADC — два зональных float-массива из зеркал field store (по контексту stage E §4 — усреднённые/экстремальные температуры зон), CB60 — второй измеряемый массив (копия из field store в FUN_181f59e0), C9CC — целевые значения зон со сдвигом ±0.75, C9AC — взвешенные отклонения (вклады demand), CD44 — их итог после обработки FUN_180c62fc. Единицы и точная физическая роль массивов — вне статического разрешения; формулы выше дословны.

### 3.8 Семейство таблиц CC04/CC1C/CC34 — FUN_181f07ec

## 5. Что это значит для эмулятора 0x20 (сводка происхождения)

Цепочка demand целиком, от первоисточников:

```
field store (поля 1, 3, 8, 0x2D, 0x2F, 0x31, 0x3E, 0x27, 0x36, 0x4A, 0x53, 0x54, 0x6C, 0x70, 0xBF, 0xCD, 0x37, 0x38, 0x47, 0x48)
 + зеркала 0xFFF82xxx/0xFFF83xxx + словарь 0x3C0Dxxxx
   → FUN_181f5d08: {FUN_181f54e8, FUN_181f59e0, FUN_181f07ec, FUN_181f21d4, FUN_181f5d8a}
   → CC52 (класс), CCC4/CCDC/CD04 + CC04/CC1C/CC34 (таблицы), CC5A (индекс),
     CABC/CADC/CB60 (зональные массивы), CABB/CB58/CB5C (входы §4), CD7D (режим)
   → FUN_181f4308: CD8C (интерполяция таблиц), C8CC (сплит по зонам)
   → refresh FUN_181efdfc: FUN_1816deec (C9CC = база ± 0.75), FUN_1816e2dc (C9AC = CA04·Δ),
     FUN_1814c9ba (CC5A/CD78), FUN_180c62fc (CD44 = Σ вкладов)
   → потребители stage E: staging FUN_180c54d8 (CCC4[CC5A−1] × 1.25/0.25/0.01),
     квантователь FUN_180c576c, арбитраж FUN_180c5832, trim FUN_180c55f2, cap FUN_18051e4e
```

Первоисточник всех ветвей — **field store и его зеркала**, т.е. данные комишенинга и шины, а не прошивочные таблицы. Это согласуется со stage D (базы оборудования в прошивке нет) и закрывает вопрос stage E «откуда берутся входы модуля»: модуль — вычислитель над зеркалом состояния системы.

## 6. Поправки к stage E

1. **FUN_181f21d4 — не потребитель, а главный производитель** таблиц CCC4/CCDC/CD04, индекса CC5A, флагов CCF4/CC5B и (в строковых ветках) массивов CC64/CC7C/CC94/CCAC и зональных записей C810+.
2. **CC52 — 16-битное слово класса оборудования**, пишется чтением поля 1 field store; «mode nibble» — лишь способ чтения его младшего нибла одним из потребителей.
3. **Ярлыки массивов §4/§7 stage E уточнены:** FUN_1816deec пишет C9CC (не CABC); FUN_1816e2dc пишет C9AC (не CB60). CABC/CADC наполняются копиями из зеркал 0xFFF83C58/0xFFF83C38 в FUN_181f54e8; CB60 — копией из field store в FUN_181f59e0. Атрибуции классификатора «1816deec→CABC/CADC idx» и «1816e2dc→CB60/C9CC idx» — артефакты оконного трекинга (в этих функциях базы только читаются), опровергнуты декомпиляцией с разрешением pool.
4. **CD44 имеет второго писателя** — FUN_180c4322 (ветка селектора 2 диспетчера FUN_180c406e), вне refresh-цикла.
5. **C90C пишут двое:** FUN_181f4308 (C90C = CD8C) и FUN_180c62fc (аккумулятор суммы → CD44); порядок внутри цикла определяет, чьё значение видит потребитель, — статически порядок между FUN_181f4308-цепочкой и refresh не установлен.

## 7. Не изолировано

- **[F] Писатели не найдены ни одним каналом у 7 ячеек:** 0xFFF8CA48, 0xFFF8CA4C, 0xFFF8CA58, 0xFFF8CA64, 0xFFF8CA68, 0xFFF8CA90, 0xFFF8CAA4. Все — второстепенные параметры зоны CAxx, в образе только читаются. Вероятные механизмы вне покрытия метода: generic property setter-ы Clarinox с рантайм-вычисляемым адресом, либо записи через базы ниже 0xFFF8C800 с регистровым смещением. Ни одна не является входом stage E.
- **[I] 0xFFF8CC6C** — писателя нет как у самостоятельной ячейки; это элемент [2] массива CC64 (база CC64 пишется indexed в строковых ветках FUN_181f21d4), а отдельный pool-адрес CC6C используют читатели.
- **Граничные ячейки вне диапазона ценза:** CE60/CE64 пишет FUN_180c62fc (декомпиляция); запись C5A0 (источник CD7D) делает FUN_181f4308 копией из 0xFFF82E0D; производители самих зеркал 0xFFF82xxx/0xFFF83xxx и field store — слой stage C, здесь не разбирались.
- **FUN_181f5928** (второй вызываемый FUN_181f5d08) не декомпилирована — её записи покрыты общим цензом (функция присутствует в appendix-таблице, если пишет в блок), но построчная семантика не разбиралась.
- **Класс оборудования Антона (значение CC52)** статически не определяется — нужен живой снимок field store/зеркал.
- Порядок выполнения FUN_181f4308-цепочки относительно refresh FUN_181efdfc (вопрос §6.5) статически не установлен.
